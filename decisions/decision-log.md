## 2026-09-08 — Выполнен план исправлений из аудит-диффа (`01_vibe-coding-agent/reports/2026-09-08_Squeezer_fix-plan.md`): восьмой demo-скрипт, pytest в CI, матрица Python, CHANGELOG; адреса ProxyAPI — НЕ сделаны, найдено расхождение с планом

**Вопрос**: план из пяти обязательных шагов (строго последовательных
первые три) плюс необязательный шестой. Порядок был важнее содержания:
шаги 2-3 бессмысленны без шага 1.

**Решение**:

1. **П-1 — `tests/integration/test_vectorizer_integration.py` перенесён
   в `examples/demo_vectorizer_integration.py`** (`git mv`, история
   сохранена). Файл — demo-скрипт (docstring прямо называл его
   «Тестовый скрипт», ноль функций `test_*`, весь код на уровне
   модуля), делавший реальный вызов OpenAI Embeddings API при каждом
   сборе `pytest` (тест 5, глушился внешним `try/except`, поэтому
   незаметно). Тот же класс проблемы, что чинили 01.09 для семи других
   файлов — этот восьмой уцелел, лежал в подпапке `integration/`, под
   неё не проверяли отдельно. Докстрингу добавлено явное предупреждение
   про живой API-вызов. Проверено: `pytest --collect-only` — 79 тестов,
   скрипта в списке нет.
2. **П-2 — `pytest tests/ -q --cov=src --cov-report=term-missing`
   добавлен в джоб `Test`** после установки `pip install -e ".[test]"`
   (extra уже был в `pyproject.toml`, просто не ставился). До этой
   правки джоб проверял только импорт пяти библиотек, `--help` и
   `VERSION` — зелёный статус не значил «тесты проходят», только
   «зависимости ставятся».
3. **П-3 — матрица Python дополнена `3.12`/`3.13`/`3.14`** (было
   `3.8`-`3.11`; проект реально работает на 3.14). **Нижняя граница
   (`requires-python = ">=3.8"`) не тронута** — решение владельца,
   план прямо просил не трогать. Локально доступны только Python 3.14
   и 3.10 (запись в реестре `py`-лаунчера для 3.10 оказалась
   устаревшей — папки `C:\Program Files\Python310\` не существует), на
   3.14 — `79 passed`, строгий `flake8 --select=E9,F63,F7,F82` — 0
   находок. Фактический ответ про совместимость с 3.8/3.9 предыдущего
   без реального прогона на CI-матрице получить нельзя — это первый
   раз, когда `pytest` в CI вообще будет запущен (см. п.2), поэтому
   ответ появится только после пуша и наблюдения за прогоном.
4. **П-4 — `actions/checkout` и `actions/setup-python` подняты до
   `v7`** (были `v3`/`v4`) во всех трёх джобах (`lint`, `test`, `build`)

   `engineering-pdf-extractor` (та же организация, тот же паттерн).
5. **П-5 — `CHANGELOG.md` дополнен разделом `[Unreleased] - 2026-08-30
   — 2026-09-08`** — материал взят из существующих записей этого же
   журнала (30.08-01.09) плюс сегодняшняя работа (пп. 1-4 выше), без
   восстановления по памяти. Версия сознательно не присвоена — решение

6. **П-6 (адреса ProxyAPI) — НЕ сделан, и не только потому что
   «не срочно».** План описывал задачу как «ядро проекта уже на
   `/v1`, хвосты `/openai` и `/anthropic` — в 4-5 файлах»
   (`llm_chunker.py`, `gui_app.py:965`, `utils/check_models.py`,
   `docs/guides/PROXYAPI_GUIDE.md`, `examples/demo_final_system_test.py`).
   Проверка по коду (`grep -rn proxyapi.ru`) нашла другую картину:
   путь `api.proxyapi.ru/openai/v1` и `api.proxyapi.ru/anthropic`
   (путь-в-URL, старая форма) действительно встречается только в этих
   5 местах — но **весь `src/` (больше 40 мест: `rag_engine.py`,
   `vectorizer.py`, `answer_generator.py`, `hyde_search.py`,
   `self_rag.py` и далее по всем модулям, плюс `squeezer.py`,
   `gui_app.py`, `batch_process.py`, `config.json`, `.env.example`,
   большая часть `docs/`) использует третью форму —
   `https://openai.api.proxyapi.ru/v1` (поддомен-в-хосте)**. По
   авторитетному источнику плана же (`01_vibe-coding-agent/scenarios/
   llm-connections.md`, раздел «ProxyAPI: один адрес вместо пяти»,
   строка 97) именно эта форма (`openai.api.proxyapi.ru/v1`) прямо
   перечислена как ОДИН ИЗ ПРЕЖНИХ (отключаемых 01.02.2027) адресов —
   то есть «ядро на /v1» в плане не соответствует фактическому
   состоянию: ядро (`src/`) целиком на другом устаревшем адресе,
   просто не на том, который план успел заметить. Настоящий единый
   адрес — `https://api.proxyapi.ru/v1` (без поддомена, без
   пути-провайдера) — в коде проекта не встречается ни разу.
   Реальный объём переноса на порядок больше заявленного (весь `src/`
   с параметрами по умолчанию в сигнатурах функций, а не 5
   файлов-хвостов) — это не «попутная правка адреса в доке», а
   отдельная задача с собственным анализом (что из ~40 мест —
   default-параметр публичного API модуля, что — внутренний вызов) и
   отдельным подтверждением объёма у владельца. Не тронуто ничего —
   ни узкий (пять файлов), ни широкий (весь `src/`) вариант; оставлено
   как открытая находка для отдельного разговора.

Дополнительно (не было отдельным шагом плана): каталог
`tests/integration/` удалён — стал пустым после переноса единственного
файла.

**Причина**: порядок «убрать риск платного вызова → включить pytest в
CI → расширить матрицу → обновить Actions → CHANGELOG» — именно такой,
как в плане, потому что каждый шаг бессмыслен без предыдущего (нет
смысла чинить матрицу для тестов, которые не запускаются; нет смысла
запускать тесты, пока сбор тянет платный вызов). П-6 отложен целиком,
а не выполнен в узком (неверном) объёме — правка по факту неполного
адреса оставила бы проект с ещё большей путаницей (три разных формы
адреса вместо двух), а не с одной.

## 2026-09-01 — Разобраны 6 сбоев тестов, впервые ставших видны после починки сбора pytest — `pytest tests/` теперь 79/79

**Вопрос**: владелец попросил разобрать 6 сбоев тестов (2 давно
известных несвязанных, 4 впервые увиденных после того, как в этой же
сессии починили краш сбора `pytest tests/`).

**Решение**:

1. **`test_chunker.py::TestValidateChunks` (3 сбоя) — неправы тесты,
   не код.** Тесты проверяли форму `{"total": ..., "empty": ...,
   "avg_length": ...}`, которой у `validate_chunks()` никогда не
   было. Реальная, нагруженная форма (`stats.total_chunks`,
   `stats.avg_char_count`/`min_char_count`/`max_char_count`,
   `empty_chunks` как список индексов) используется по всему
   проекту — `gui_app.py`, сам `chunker.py` (генерация отчёта),
   `vectorizer.py`, `examples/demo_vectorization.py`,
   `tests/integration/test_vectorizer_integration.py`. Переписаны
   3 теста под реальную форму.
2. **`test_vectorizer.py::test_empty_dataset` — прав тест, не хватало
   ключей в коде.** `save_to_vector_db([])` (пустой датасет) возвращал
   `{"success", "embeddings", "embedding_dim", "vector_db_path",
   "dataset_path"}` — без `metadata_path` и `total_vectors`, которые
   есть в успешном пути (`return` в конце функции). Добавлены оба
   ключа в ранний `return` — теперь форма согласована независимо от
   того, пустой датасет или нет.
3. **`test_preprocessor.py::test_empty_input` — реальный баг.**
   `normalize_text(None)` возвращал `None`, а не `""` (`return
   cleaned_text` вместо `return ""` в раннем выходе для пустого
   ввода) — `clean_text()` тот же паттерн обрабатывает верно, только
   `normalize_text()` был не согласован. Исправлено.
4. **`test_preprocessor.py::test_detect_paragraphs` — реальный баг.**
   `structure_text()` не сбрасывал `current_paragraph` на пустой
   строке — несколько абзацев, разделённых пустой строкой,
   склеивались в один при финальной сборке. Добавлен flush на пустой
   строке (тот же паттерн, что уже был у заголовков/списков).
   **Проверено на реальном документе ФИПИ** (том самом, что уже
   перечанкован и переэмбеддён в 157 чанков, см. записи выше): сумма
   абзацев/заголовков по всем 18 страницам до и после фикса —
   одинаковая (53/21) — у pdfplumber внутри одной страницы просто не
   возникает двойных пустых строк, поэтому баг реален, но на уже
   готовых 157 чанках не сказался. **Переэмбеддинг не потребовался.**

`pytest tests/` — 79/79, зелёный впервые за всё время существования
файла (раньше сбор всего набора падал раньше, чем доходил до этой
проверки). Строгий `flake8 --select=E9,F63,F7,F82` — чисто.

**Причина**: расследование каждого сбоя дало на выходе 2 разных
класса решения (тест был неправ / тест был прав, код неправ) — важно
не чинить наугад, а определить источник истины по факту (реальные
вызывающие места в коде, а не intuition), что и было сделано для
каждого из 4 отдельных случаев.

токенов) — минимальная, но сам факт непреднамеренного вызова стоит
зафиксировать честно.

сохранена) под именами `demo_*.py` — совпадает со сложившейся

`run_test.py` не тронут — не совпадает с паттерном сбора pytest'а
(`test_*.py`, не `*_test.py`), реальной опасности не представляет,
хоть и той же природы скрипт.

Результат: `pytest tests/` теперь реально досчитывает набор до конца
(раньше падал на сборе с «collected 0 items» и невнятной ошибкой
про закрытый файл захвата вывода) — 73 из 79 настоящих тестов
проходят. Оставшиеся 6 провалов — не моя правка: 2 уже известны и
не связаны (`test_empty_input`, `test_detect_paragraphs` в
`test_preprocessor.py`, задокументированы раньше), ещё 4 новых
(`test_chunker.py`×3, `test_vectorizer.py`×1) — раньше физически не
могли быть увидены, потому что сбор тестов падал раньше, чем
доходил до этих файлов. Не разбирались — отдельная находка, не
входила в объём этой задачи.

**Причина**: молчаливый крах сбора всего набора тестов из-за одного
неудачно названного файла — плохой знак сам по себе; то, что

## 2026-09-01 — Данные ФИПИ, шаги 1-2: экстрактор переключён на pdfplumber, найден и исправлен второй баг в structure_text()

**Вопрос**: продолжение находки «качество данных ФИПИ» (см. ниже) —
владелец предоставил исходный PDF (`pdfs/2_obshchestvoznaniye-oge.pdf`,
не в git — `pdfs/*.pdf` в `.gitignore`) и подтвердил план из двух
шагов без API: (1) сравнить `pypdf` vs `pdfplumber` на уже известных
испорченных местах, (2) разобраться, почему кодификатор тем на стр. 4
резался на бессмысленные обрывки-«заголовки».

**Решение**:

1. **Экстрактор переключён на `pdfplumber`.** Прямое сравнение на
   известных плохих местах (стр. 1-3) — `pdfplumber` даёт чистый
   текст: «В ам»→«Вам», «(О ГЭ)»→«(ОГЭ)», «хорош ую»→«хорошую»,
   «м атериалов»→«материалов», обрыв на «котор[ых]» исчез. Прогон по
   всем 18 страницам документа — ни одной страницы с оставшейся
   порчей текста (кроме одной декоративной, изначально
   разрежённой по буквам, надписи на обложке — сама вёрстка PDF, не
   баг экстрактора). `extract_text_from_pdf()` теперь пробует
   `pdfplumber` первым, `pypdf` — фолбэк, если `pdfplumber` не
   установлен (он уже был в `requirements.txt`/`pyproject.toml`,
   использовался только в `table_extractor.py`). В метаданные каждой
   страницы добавлено поле `extractor` — какой метод сработал.
2. **Найден второй, независимый баг — в `structure_text()`.**
   Раньше он не рассматривался как отдельная находка (числился
   частью «обрыва слов на границе чанкинга»). Причина: заголовки
   определяются построчно, а строки — это визуальные переносы PDF, не
   границы предложений. `re.match(..., re.IGNORECASE)` в эвристике
   заголовка позволял и заглавным, и строчным строкам подряд, без
   разбора, была ли предыдущая строка окончена. Итог — перенесённый
   на вторую строку хвост одной и той же фразы в узкой колонке
   таблицы («3.2 Товары и услуги, ресурсы и потребности,» +
   «ограниченность ресурсов» второй строкой) распознавался как
   отдельный самостоятельный заголовок. Исправлено: эвристика
   заголовка (кроме однозначного markdown `#...`) теперь срабатывает

## 2026-09-01 — Аудит-diff Squeezer с момента прошлого аудита (2026-08-30): собственная правка abbr-фикса пересмотрена и улучшена

записи выше про качество данных.

Остальные 6 углов (B-исходный, E/wrapper, reuse, efficiency,
conventions) — без находок; кандидат от simplification (та же
дупликация) уже учтён выше.

## 2026-09-01 — Качество данных ФИПИ: найден и исправлен баг в normalize_text(), чанки-мусор не тронуты (нет исходного PDF)

**Вопрос**: OGE-Tutor'овская проверка качества контента (Находка 1,
`OGE-9-Tutor-GUI-Assistant/decisions/2026-09-01_content-quality-review.md`)
нашла в реальной базе ФИПИ (`RAG_data_base/vector_db/dataset.json`,

текст и обрыв слов на границе чанкинга. Разбор на месте (прямое
чтение `dataset.json`) уточнил и частично пересмотрел эту находку:

1. **Подтверждено и исправлено — баг в `normalize_text()`.**
   `src/preprocessor.py` разворачивал сокращения (`ABBREVIATIONS`)
   уже после приведения текста к нижнему регистру, простой
   регистрозависимой заменой подстроки. Инициалы человека, случайно
   совпадающие по буквам с сокращением («Т.Е. Лискова» → нижний

   того же автора ФИПИ) оказались багом; остальные 11 — корректные

   т.д.), их трогать было нельзя. Исправлено переносом разворачивания
   сокращений до `lower()` — теперь совпадение регистрозависимое, и
   инициалы (заглавные) больше не задеваются, а обычные инлайновые
   сокращения (строчные в оригинале) разворачиваются как раньше.
   Затрагивает оба режима — `preserve_structure=True` и `False`.

   трогались).
2. **Частично сделано — 7 чанков чистого мусора убраны из живой

   заголовка документа, имя издателя, «Москва, 2020» и один чанк,
   являющийся чистым артефактом OCR (буквы через пробел). Нулевая
   образовательная ценность, уверенность высокая (это буквально

   `OGE-9-Tutor-GUI-Assistant/RAG_data_base/vector_db/` (все три

   существующего индекса и добавлены в новый в сохранённом порядке,

   Проверено self-retrieval тестом на пересобранном FAISS-индексе

3. **Не сделано — требует решения владельца.** Более глубокая

**Решение**: закоммичен только безопасный, проверяемый без внешних

**Причина**: полный передел данных требует стоящих денег вызовов

это автономно без осведомлённости владельца о стоимости. Разделение

## 2026-08-30 — CI зелёный впервые в истории проекта

**Вопрос**: после пуша фикса `PyPDF2`→`pypdf` и `F821`-бага (запись
ниже) прогон CI всё ещё падал — оказалось, что маскировавшихся причин
было больше одной.

**Решение**: последовательно исправлены ещё три независимые находки,
каждая подтверждена реальным прогоном на GitHub (`gh run watch`) перед
переходом к следующей:
1. `src/preprocessor.py:205` — `-> str | tuple` (PEP 604) требует
   Python 3.10+, а `pyproject.toml` объявляет `>=3.8` и CI тестирует
   3.8/3.9 — падало с `TypeError`. Исправлено `from __future__ import
   annotations`.
2. `squeezer.py --help` — падал на Windows с `UnicodeEncodeError`:
   справка на русском, консоль Windows по умолчанию `cp1252`, не умеет
   кириллицу. Затрагивало не только CI, а любого реального
   Windows-пользователя без настроенной UTF-8-консоли. Исправлено
   принудительным `sys.stdout/stderr.reconfigure(encoding="utf-8")`.
3. `actions/upload-artifact@v3` в `Build`-job — устарел, GitHub
   автоматически проваливает такие workflow. Поднято до `@v4`.

После всех четырёх правок (считая `PyPDF2`/`F821`) прогон
`33332914877` завершился `success` по всем job: `Lint`, все 12
комбинаций `Test` (3 ОС × 4 версии Python), `Build`.

**Причина**: находки вскрывались одна за другой — каждая следующая
была замаскирована предыдущей (job падал раньше, чем доходил до
следующей причины). Владелец подтверждал каждую правку по отдельности
перед тем, как переходить к следующей.
